Windows Authentication from ROSA to SQL Server

How a Python app in a Linux container on ROSA HCP logs in to SQL Server on EC2 as an Active Directory service account, using Kerberos and a sidecar container. Names such as corp.example.com, sql01 and svc-app are placeholders.

1 · End to end 2 · Inside the pod 3 · One login, step by step 4 · Rotating the keytab 5 · Network flows

1 · End to end: what talks to what

Every arrow is a connection the pod opens, plus two set up by the platform (the keytab mount and the domain membership of SQL Server). Three leave the cluster: DNS to resolve AD names, Kerberos on port 88 to the domain controllers, and the database connection on port 1433. The AD domain is not chosen yet, so the right-hand zone stands for either variant.

Inside ROSA HCP

  • The app pod holds two containers: the Python app and a Kerberos sidecar.
  • The keytab Secret is mounted into the sidecar only.
  • Cluster DNS answers cluster names and passes the rest upstream to the VPC resolver.
  • Pod traffic leaves with the worker node's IP, which changes. Firewalls allow the worker subnets, or a fixed EgressIP.

In AWS

  • A Route 53 Resolver rule sends corp.example.com queries to the AD DNS servers. The cluster needs no change.
  • SQL Server runs on EC2, joined to the domain, on static port 1433.
  • Its security group must allow 1433 from the worker subnets.

In Active Directory

  • Domain controllers run the KDC on port 88, and usually DNS on 53.
  • Variant A: corporate DCs over Transit Gateway and Direct Connect or VPN.
  • Variant B: AWS Managed Microsoft AD in a peered VPC.
  • The service account lives in SQL Server's domain, so there is no cross-realm step.

2 · Inside the pod

On Windows the operating system handles Kerberos for you; here two containers do it by hand. One container owns the secret and keeps a ticket fresh; the other only reads that ticket. The left zone holds the OpenShift objects the pod mounts.

Kerberos sidecar

  • Mounts the keytab and krb5.conf; runs kinit -kt every hour.
  • AD tickets last 10 hours by default, so an hourly refresh leaves a wide margin.
  • As a native sidecar (init container with restartPolicy: Always) it starts before the app and stops after it.
  • Image: UBI plus krb5-workstation for kinit and klist.

Ticket cache

  • An emptyDir with medium: Memory, so the ticket never touches disk.
  • Both containers set KRB5CCNAME=FILE:/var/kerberos-ccache/cache. The RHEL default KEYRING: cache is the wrong type for sharing.
  • MIT Kerberos writes the file as 0600, so both containers must keep the same UID.

App container

  • Python, pyodbc, unixODBC, ODBC Driver 18 and the MIT Kerberos libraries.
  • Trusted_Connection=yes with the server's FQDN, and no UID or PWD.
  • Never sees the keytab. It asks the KDC for the SQL Server ticket itself, using the TGT from the cache.

3 · One login, step by step

Nine messages in three phases: the sidecar gets a ticket-granting ticket, the app trades it for a ticket addressed to SQL Server, and SQL Server checks that ticket with its own key. The password never crosses the network.

Steps 1 to 3: the TGT

  • The sidecar proves it holds svc-app's key by sending a timestamp encrypted with it (pre-authentication).
  • The KDC answers with a TGT valid for about 10 hours.
  • The sidecar writes it to the shared cache and repeats every hour.

Steps 4 to 6: the service ticket

  • The ODBC driver builds the SPN MSSQLSvc/sql01.corp.example.com:1433 from the server name.
  • The KDC encrypts the ticket with the key of the account that owns that SPN.
  • A missing or duplicate SPN fails here, with no NTLM fallback on Linux.

Steps 7 to 9: the login

  • The ticket travels inside the TDS login packet.
  • SQL Server decrypts it with its own key and maps it to CORP\svc-app. It may still ask a DC for group data, but it does not need the KDC to accept the ticket.
  • To confirm, check that auth_scheme reads KERBEROS.

4 · Rotating the keytab

A keytab holds keys derived from the account password. Change the password and every copy of the old keytab stops working, so rotation follows a fixed order: new keys first, password second.

Safe order

  • Build keytab entries for the next kvno and keep the current ones.
  • Update the Secret. The sidecar picks up the new file at its next kinit.
  • Change the password in AD to the value used for the new entries.
  • Remove the old kvno entries once everything works.

What breaks it

  • Changing the password first: kinit fails until the new keytab arrives.
  • A 90-day password expiry with no rotation plan.
  • A keytab with only RC4 keys. Domain controllers assume AES-only since the 2026 updates.

Who owns what

  • AD team: the keytab, the password and the kvno.
  • Platform team: the Secret store and who can read it.
  • Security: a never-expires exception, or the rotation schedule.
